Time Tracker architecture

Time Tracker shares one Rust core across a terminal UI, an automation CLI and a native macOS app. Each client either opens a local SQLite database or sends the same actions to tt-server, which owns its own SQLite database. Domain rules and persistence live in Rust; clients own presentation, input and scheduling (ADR 0021, ADR 0028). Method-level diagrams of the clients and the Swift-to-Rust bridge are in diagrams.html.

Domain language

  • Task: a reusable activity with a validated name, an archive flag and creation and update timestamps. Archiving keeps its worklogs. Owner: task model (ADR 0002, ADR 0009).
  • Worklog: a recorded interval owned by one task; without an end it is active. Intervals include their start and exclude their end, must have a positive duration and can't overlap within one task. Owner: worklog model (ADR 0005, ADR 0007, ADR 0008).
  • Active tracking: the tracker is idle or runs one worklog across the database. Switching stops the old worklog and starts the new one atomically; closing a client leaves tracking running. Owner: tracking model.
  • Operation instant: the time a client supplies for an action. The application canonicalizes it to UTC microseconds; calendar boundaries use time zone rules (ADR 0003, ADR 0006).
  • History page: up to 50 worklogs, newest start first, continued with a cursor holding the last ID and a database counter (ADR 0004, ADR 0024).
  • Report: task totals for an interval. Running work is clipped at an explicit cutoff and archived tasks stay included. Owner: report use cases.
  • Inactive-task archive preview: the tasks without creation, change or work within a period, 14 days by default, captured at a fixed time. Confirmation rechecks eligibility in one transaction (ADR 0016).
  • Reviewed values: the values a user saw before a write, such as a task name or the active worklog. Guarded writes carry them, and storage rejects the write when the stored values differ (ADR 0023).

Context

One person uses the application, usually in one window at a time. Several clients and machines can change the same data, but the design doesn't optimize for it: rejecting an outdated write and asking for a reload is acceptable.

Processes

Each client selects its mode at startup: tt and tt-cli take --server URL, tt-cli also takes --db PATH, and the macOS app reads its Settings. Remote failures never fall back to local storage. Local clients can open the same tt.db at the same time; SQLite transactions and triggers keep them consistent. The macOS app links tracker-swift-bridge as a static library and calls it through a C ABI on one serial worker, so it is one process. Deploy a server describes how tt-server is built and rolled out.

Modules and dependencies

Arrows show permitted dependencies. For Rust crates, the Cargo manifests are the rule: a crate can only use the workspace crates it declares. The TrackerClient Swift package declares no Rust, network or UI dependency.

Which core crates each application may use:

ApplicationRust core crates
tracker-tuiclient, application, domain, remote, storage
tracker-cliclient, application, domain, protocol, remote, storage
tracker-swift-bridgeclient, application, domain, protocol, remote, storage
tracker-server-appserver, storage

Inside a crate or app, code is split by feature. Features may depend on other features but not in a cycle; the compiler doesn't catch cycles between folders, so review does.

In the Swift app and package, folders in a target must not form a cycle, and App/ counts as an ordinary folder. Review checks each target separately, and same-named feature folders in the two targets are separate nodes (ADR 0034). Shared/ holds helpers no feature owns and Contracts/ holds protocols and wire models (ADR 0030). An app feature folder whose store lives in the package uses the package folder's name, such as Features/WorklogCorrection in both targets.

Module responsibilities

  • tracker-domain: task and worklog identities, validated names, interval rules, tracking transitions and inactivity periods. No database, network or UI work; operation instants are inputs.
  • tracker-application: synchronous use cases through one TrackerRepository contract, calendar and search policies, and semantic failures (ADR 0012, ADR 0022).
  • tracker-storage: SqliteRepository implements the repository contract with database paths, migrations, coherent reads and transactional writes. Constraints and triggers also guard direct SQL writes.
  • tracker-protocol: protocol 6 JSON requests, resource reads and command receipts, and parse_worklog_cursor, the one cursor validation rule. No HTTP client, server or database (ADR 0017, ADR 0031).
  • tracker-server: HTTP routes, serialized operations, request-ID receipt replay and coherent aggregate reads (ADR 0019, ADR 0027).
  • tracker-remote: RemoteApplication sends reviewed values without reading first, validates responses before publishing them and recovers after failed writes (ADR 0018).
  • tracker-client: the TrackerBackend enum, which dispatches task, tracking, history, report and archive operations to the local application or RemoteApplication.
  • tracker-tui: the tt client. One event loop handles input, redraw ticks and request completions; a monotonic clock drives the elapsed timer (ADR 0011).
  • tracker-cli: the tt-cli client. Invalid input fails before a backend opens; see the command reference.
  • tracker-server-app: tt-server requires an explicit loopback or Tailscale bind address and defaults to tt-server.db.
  • tracker-swift-bridge: the C interface of the Rust static library. Rename, archive, tracking and worklog writes carry the reviewed values. Create (tt_bridge_create_task_at), restore (tt_bridge_unarchive_task_at) and bulk archive (tt_bridge_archive_inactive_tasks_at) carry none.
  • TrackerClient: feature state, TrackerFeatures and TrackerSync behind injected client, report, clock, scheduler and settings interfaces. Each action sends its request right away; each feature disables only its own controls while a request runs (ADR 0026, ADR 0029). Views read the task list, tab and selection from the observable TaskCatalogStore, the selected task's worklogs from WorklogHistoryStore, the connection settings and status from ConnectionStore, the running worklog, tracking error and timer text from TrackingStore, today's status and task totals from DailyTotalsStore, the auto-pause preference and status from TrackingAutomationStore, whether tracking can start or stop from TrackingAvailability, and each dialog's state from its own feature store (ADR 0030). The menu bar observer reads these stores, the last tracked task from MenuBarStore and the start and stop checks from TrackingAvailability through one Observations loop, and TrackerMenuSources computes the running task's name from the connection, tracking and catalog stores. TrackerSync loads, refreshes and polls the stores, handles visibility, sleep and wake, switches the connection, and reloads after dialog writes (ADR 0032). Each store keeps its own observed values current. Shared/DisplayClock ticks every second while a window or the menu shows a running worklog, and every minute while the menu bar shows today's total; TrackingStore refreshes the timer text and DailyTotalsStore today's totals on each tick (ADR 0039). On a connection change TrackerSync calls acceptConnection, in a fixed order, on each store that holds state of the previous connection (ADR 0038). It hands a loaded task list to the stores in a fixed order through their acceptTaskList methods and passes the values one store needs from another, such as the running worklog before and after the update. WorklogHistoryStore decides from them whether to reload or clear its error. DailyTotalsStore requests and checks today's report when TrackerSync asks it to, runs the midnight rollover timer, and hands the task list that comes with the report back to TrackerSync. It reads the tasks from TaskCatalogStore and the running worklog from TrackingStore, so TrackerSync hands it each task list after those two. TrackingAvailability reads the connection, catalog and tracking stores to decide which tracking requests are possible. TrackingStore starts and stops tracking after asking it, and MenuBarStore runs the status item's primary action through TrackingStore. The app turns the display clock's minute ticks on and off through MenuBarStore while the menu bar shows the daily total. TrackingStore cancels a pending auto-resume and reloads the task list through closures that TrackerFeatures sets, so Tracking doesn't depend on TrackingAutomation. It shows a failed request's error once that reload returns. TrackingAutomationStore pauses the running timer when the screen locks and resumes its task when the screen unlocks. It records and shows failures on TrackingStore directly, and reloads through a closure that TrackerFeatures sets. TrackerFeatures, which TrackerAppRuntime and the test fixture create, creates and holds the stores, TrackingAvailability, TrackerMenuSources and TrackerSync, and passes the dialog stores TrackerSync's reloadAfterTaskWrite(then:) or reloadAfterWorklogWrite() as their reload closures. TaskCreationStore also gets TaskCatalogStore.showTask(_:) and BulkTaskArchivingStore gets recordReadFailure(_:). The dialog stores and TrackingStore also share one Shared/PresentationGate, which a dialog store claims while its sheet shows and TrackingStore claims while its error alert shows. A dialog store's canOpen is false while the gate is claimed, so a person can't open a second dialog (ADR 0036). A store that reopens its own dialog after a failed write, such as a failed unarchive, doesn't check the gate, so that dialog can still show behind another one. Settings checks a connection with the stateless testConnectionSettings function, which leaves the current connection unchanged. Views change the tab and selection on TaskCatalogStore, and retry the history and load older pages on WorklogHistoryStore. A tab or selection change reloads the history through a closure that TrackerFeatures points at WorklogHistoryStore. WorklogHistoryStore reads the selection from TaskCatalogStore and the stale connection from ConnectionStore, sends its own page requests, and reports each failure through a closure to TrackerSync, which records connection failures that ConnectionStore says need recovery. Views connect and retry on ConnectionStore and turn the auto-pause on or off on TrackingAutomationStore. Through closures that TrackerFeatures sets, ConnectionStore lets TrackerSync switch the connection and refresh. Turning the auto-pause on while the screen is locked pauses a running timer. No view reads TrackerSync. User actions live on the store of the feature that owns them. A view reads that store from the environment, and a package store reaches TrackerSync only through a closure that TrackerFeatures passes (ADR 0035).
  • TimeTrackerSwiftUI: one tracker window, Settings, the menu bar item and lifecycle handling. The serial TrackerWorker keeps bridge calls and decoding off the UI thread and runs them in order.

Runtime flow

The worker lane covers TrackerWorker, the tt_bridge_start_tracking_if_active_at export of tracker-swift-bridge and TrackerBackend in tracker-client. Replies run back through it; the diagram skips those hops. The reload reads /v1/state/task-list first only while the connection is unconfirmed or stale. The transport resends a failed write once with the same request ID. If that also fails, the app reports that the change could not be confirmed and doesn't resend it.

Revisions and concurrency

The server keeps no global revision. Guarded writes carry the values the caller reviewed, and the shared application and storage operations compare them with stored state in the same transaction as the write. Database counters guard history paging in local and remote mode.

MechanismStored inProtects against
Reviewed valuesThe requestA write based on an outdated worklog, active timer or task name
Request IDServer memory, at most 1,024 successful receiptsA resent command running twice while its receipt is cached
Per-task history counterhistory_order_revision on each taskContinuing a task's history after a worklog start changed or a worklog moved
Global history counterOne global_worklog_revision rowContinuing the all-worklogs history after any worklog write

Reviewed values. Correction compares the original worklog times; move and deletion also compare the original task. A mismatch returns HTTP 409 worklog_changed. Start and switch compare the expected active worklog; stop rejects a replacement timer and succeeds when no timer remains. Rename and archive compare expected_name when the request carries it. A changed timer or name returns HTTP 409 conflict. Writes to unrelated tasks or worklogs never reject a command. Create, restore, bulk archive, and rename or archive without expected_name carry no reviewed values; tt-cli tasks rename and tasks archive send no expected name and act on the current task.

Request replay. WriteGuard.request_id identifies a command. Under the operation lock, an identical cached command returns its receipt with replayed: true; the same ID with a different command returns HTTP 409. A restart or eviction forgets receipts, so an old command can run again if its reviewed values still match. This is bounded replay protection, not exactly-once execution (ADR 0031).

Coherent reads. /v1/state/task-list and /v1/state/daily-overview read tasks, tracking and totals in one SQLite transaction under the operation lock. Separate task, tracking, history and report reads stay independent.

History counters. SQLite triggers update the counters inside the worklog write, including writes from other local processes. A continuation checks the counter, resolves its anchor by ID and reads the next rows in one transaction; a changed counter or missing anchor returns HTTP 409 worklog_history_changed and needs a fresh first page. Renames, archiving, inserts, deletions and end-only edits leave the task counter unchanged, because existing rows keep their order. The global counter changes on every worklog write.

The guards coexist because they cover different things: counters cover history order, reviewed values cover the state a command was reviewed against, and both also apply to local clients that never reach the server.

Tests and quality gates

Unit tests sit next to the code. Black-box E2E tests drive the clients and the HTTP API through their public interfaces. Before handoff, run cargo fmt --all --check, Clippy with warnings as errors, the Python script tests, cargo llvm-cov for the full test suite with coverage and cargo crap. Swift changes also run scripts/swift-style.py. Mutation checks with cargo-mutants and scripts/swift-mutations.py cover the files a task changed (ADR 0014).

CI runs formatting, lint and Python tests, Rust tests with coverage and CRAP, Swift style, tests and coverage on Linux, a focused Swift mutation check on pull requests, and native macOS UI tests (ADR 0015, ADR 0025). Full Rust and Swift mutation runs are manual.
