Architecture primitives

tracker-domain

Owns task and worklog identities, validated names, interval rules, tracking transitions, and inactivity periods. Its models validate changes without performing database, network, or UI work. Operation instants are explicit inputs.

Depends on: no other repository component.

Source: crate, models. Decisions: ADR 0005, ADR 0016.

tracker-application

Owns synchronous use cases, calendar and search policies, and semantic failures. TrackerApplication<R> coordinates domain rules through one TrackerRepository contract. TrackerApplicationService remains the TUI's synchronous test boundary. Storage adapters implement persistence; clients own presentation and scheduling.

Depends on: tracker-domain.

Source: crate, use cases, repository contract. Decisions: ADR 0012, ADR 0022.

tracker-storage

Used by clients in local mode and by the HTTP server. Remote clients use HTTP instead of opening SQLite. Owns database connections, paths, migrations, coherent reads, and transactional writes. SqliteRepository implements the application repository contract. Database constraints also enforce single active tracking, same-task overlap rules, and active-worklog deletion protection for direct SQL writes.

Depends on: tracker-application, tracker-domain.

Source: crate, SQLite adapter, migrations. Decisions: ADR 0005, ADR 0007.

tracker-protocol

Defines protocol-5 JSON requests, resource observations, command receipts, and conversions at the HTTP boundary. Task rename and archive requests carry the reviewed task name as expected_name; restore carries none. parse_worklog_cursor holds the one cursor validation rule: the revision is nonnegative and the ID is a WorklogId. Observations pair read values with revisions. Receipts describe committed writes and do not replace current read state. This crate contains no HTTP client, server, or database connection.

Depends on: tracker-application, tracker-domain.

Source: crate, wire contracts. Decisions: ADR 0017, ADR 0019, ADR 0027.

tracker-server

Owns HTTP routes, server-side operation serialization, revision guards, command receipts, and its application and SQLite database. Task-list and daily-overview reads capture related resources in one transaction. Rename and archive check the reviewed task name through the shared guarded application operations, which compare and write in one SQLite transaction. tt serve launches this library against an explicit local or Tailscale bind address.

Depends on: tracker-application, tracker-domain, tracker-protocol, tracker-storage.

Source: crate, entry points, resource routes. Decisions: ADR 0017, ADR 0019, ADR 0027.

tracker-remote

Used by clients in remote mode; local clients and the HTTP server use the local application and storage path. Owns asynchronous HTTP transport, response validation, confirmed resource caches, and guarded command recovery. RemoteApplication publishes only validated observations. Failed refreshes retain confirmed values; a saved command remains saved after a display refresh fails. Unloaded tracking differs from observed idle tracking. Report requests share canonical range, query, cooldown, and echoed-context validation in ReportsClient; the coordinator validates the remaining daily-overview resources before publishing them together. A restored inactive-task preview token passes the same validation as a server preview while it is deserialized. It never opens the server's database.

Depends on: tracker-application, tracker-domain, tracker-protocol.

Source: crate, remote application, transport. Decisions: ADR 0018, ADR 0019.

Report validation scope: ff6099d4ed2e543bf1502ad926131c00b3f18293, inspected on 16 October 2026. Report requests fetch validated totals without publishing aggregate resources; the coordinator owns coherent adoption.

Preview token validation scope: 9cc4e78fa6b02c5dfa835c3572ca4f94fc60e5fc, inspected on 17 October 2026. InactiveTaskPreview deserializes through its protocol DTO and rejects tokens that fail preview validation.

tracker-client

Owns shared client dispatch through the concrete TrackerBackend enum. It selects a local application or RemoteApplication and shares task, tracking, history, report, and archive operations. Remote failure never selects local storage. Callers retain runtime, lifecycle, input, and output ownership.

Depends on: tracker-application, tracker-domain, tracker-protocol, tracker-remote, tracker-storage.

Source: crate, backend. Decision: ADR 0021.

tracker-tui

The tt terminal client owns keyboard commands, screen state, rendering, terminal restoration, and a monotonic timer. One event loop handles input, redraw ticks, and request completions. Production requests use TrackerBackend; presentation tests can inject TrackerApplicationService. The same binary launches tracker-server through tt serve.

Depends on: tracker-client, tracker-application, tracker-domain, tracker-remote, tracker-server, tracker-storage.

Source: crate, startup, controller, runtime. Decisions: ADR 0011, ADR 0021.

tracker-cli

The tt-cli automation client owns argument validation, command handlers, JSON output, exit codes, and local/remote selection. It dispatches through TrackerBackend and reuses application search and calendar policies. Invalid input fails before opening a backend. It performs no terminal rendering or raw SQL queries.

Depends on: tracker-client, tracker-application, tracker-domain, tracker-protocol, tracker-remote, tracker-storage.

Source: crate, entry point, command reference. Decisions: ADR 0012, ADR 0021.

tracker-swift-bridge

Owns the Rust static library's C ABI, connection handles, JSON results, and persistent current-thread Tokio runtime. It dispatches through TrackerBackend and maps failures for Swift. Rename and archive exports carry the reviewed task name into the shared application operation; the bridge has no unguarded rename or archive export. Restore has no name guard. Start and stop exports take the click time and check the active worklog the app last read; resume requires an idle tracker. The bridge has no unguarded tracking export. The worklog delete export requires the expected task, start, and end, so it cannot delete a running worklog. The native app's serial TrackerWorker owns call ordering and handle disposal; the bridge owns neither windows nor feature state.

Depends on: tracker-client, tracker-application, tracker-domain, tracker-protocol, tracker-remote, tracker-storage.

Source: crate, backend, C interface. Decisions: ADR 0018, ADR 0021.

TrackerClient Swift package

Owns portable feature state and TrackerSession coordination through injected client, clock, scheduler, and settings interfaces. Connection and selection generations reject obsolete results. It composes resource observations for features and separates command success from later refresh failures. Queued rename and archive intents retain their reviewed names through background updates and pass them through the client contract. Rust compares the name and writes in one transaction; a conflict requires refresh and review. Worklog deletion finds the completed row in bounded task history, then deletes it with its expected task and times. A changed row requires review. After an uncertain failure, a missing row counts as deleted. TrackerPresentation copies the session values views read into an @Observable model and assigns only changed values. Rust continues to own domain rules and persistence.

Depends on: Foundation, Observation, and injected interfaces. No direct Rust, SwiftUI, AppKit, network, or database dependency.

Source: package, session, presentation, contracts. Decisions: ADR 0007, ADR 0018, ADR 0026.

TimeTrackerSwiftUI macOS app

Owns SwiftUI scenes, views, observable stores, and feature action stores, plus AppKit menu-bar and lifecycle integration. Views read observable values directly, so SwiftUI redraws only views whose values changed. Windows share the portable session. Its infrastructure supplies preferences, timers, and the serial TrackerWorker, which keeps bridge calls and decoding off the UI thread. Window interaction and error presentation stay in the app.

Depends on: TrackerClient, tracker-swift-bridge through the C ABI, SwiftUI, and AppKit.

Source: app, worker, native architecture. Decisions: ADR 0018, ADR 0021, ADR 0026.

Application concepts

How the concepts fit together

Task

A reusable activity identified by TaskId, with a validated name, archive flag, and creation/update timestamps. Archiving preserves its worklogs. Rename, archive, and restore advance metadata time without moving it backward; tracking leaves it unchanged. Latest work is derived from worklog starts and drives the default task order. Fuzzy search ranks matches by the newer of metadata update and latest work.

Owner: task model, task list model, and search policy. Decisions: ADR 0002, ADR 0009.

Worklog

A recorded interval identified by WorklogId and owned by one task. A missing end means it is active. Completed intervals include their start and exclude their end. The end must be strictly later than the start after microsecond canonicalization; touching intervals remain valid. Same-task intervals cannot overlap; different tasks may overlap. Correction preserves identity, ownership, and active/completed state. Moving changes only ownership. Deletion requires a completed row. These writes compare the original stored values to reject stale edits.

Owner: worklog model and worklog use cases. Decisions: ADR 0005, ADR 0007, ADR 0008.

Active tracking

The tracker is idle or running one worklog across the selected database. Starting a previously stopped task creates a new worklog. Switching stops the old worklog and starts the new one atomically. A stop or switch at the active start fails and leaves tracking unchanged. Archived tasks cannot start tracking, and a running task cannot be archived. Closing a client leaves tracking running for the next client or restart.

Owner: tracking model, tracking use cases, and SQLite tracking.

Time and elapsed duration

Clients supply operation instants; the application canonicalizes them to UTC microseconds before validation and persistence. Calendar boundaries use timezone rules. The TUI anchors its live elapsed timer to a monotonic clock so wall-clock changes do not change displayed or persisted running duration. Its timestamp display and correction inputs use local minute precision while unchanged values retain stored precision.

Owner: application service, calendar policy, and TUI clock. Decisions: ADR 0003, ADR 0006.

History and cursors

Worklogs load in pages of at most 50, newest start first with ID ascending as the tie-break. Task and global cursors carry only the last row ID and their database revision. Both scopes use WorklogCursorDto in protocol pages and CLI history tokens; the token's scope field records which history the cursor belongs to. The server, remote client, CLI and Swift bridge validate incoming cursors with parse_worklog_cursor and then build their own task or global cursor. Storage resolves the anchor start and collection membership in the same transaction as revision checks and page reads. Changing a start or moving a worklog invalidates affected task cursors. Inserts and end-only edits preserve task cursors; deleting the anchor requires a fresh first page. Global revisions change on every worklog write. History is a bounded read, not the source of report totals.

Owner: page and cursor models, cursor wire format and parsing, and SQLite history reads. Decisions: ADR 0004, ADR 0005, ADR 0008.

Reports

Totals clip worklogs to a requested interval, using an explicit cutoff for running work. Archived tasks remain included. Calendar policy converts inclusive local dates to a UTC interval with an exclusive end. Shared client rows carry task IDs and durations; clients resolve labels according to their output needs.

Owner: report use cases, SQLite aggregation, and client reports. Decisions: ADR 0012, ADR 0021.

Inactive-task archive preview

A reviewed candidate set captured at a fixed time and positive inactivity period, defaulting to 14 days. Eligibility checks task creation, metadata changes, and work in that window. Confirmation rechecks eligibility in one transaction. Local confirmation guards the candidate IDs; remote confirmation guards the revision and preview expiry. tracker-remote rejects a restored remote token whose fields fail server-preview validation. Running tasks remain protected and archiving keeps history.

Owner: inactivity period and task use cases. Decisions: ADR 0012, ADR 0016, ADR 0017.

Revisions and concurrency

The server token guards remote commands and coherent resource reads. Database counters guard history pagination in both local and remote mode. These are separate version spaces, not independent general-purpose versions on every task and worklog.

Server command and resource revision

The server creates a new epoch at startup and starts its sequence at 0. Reads return the token captured under the operation lock. Writes submit expected_revision; the server checks equality under that same lock before executing a new command. A mismatch returns HTTP 409. This prevents a stale rename from silently overwriting another client's edit and rejects stale archive previews. Rename and archive also carry expected_name, which SQLite compares with the stored name in the write transaction, independent of the revision. A different name returns HTTP 409 conflict and leaves the task unchanged. Matching read tokens also let clients check that related resource observations agree.

The token covers server-mediated commands, not direct SQLite writes. It is not persisted. A restart changes the epoch, so old tokens remain invalid even though the sequence resets. Identical successful request replays are checked before the revision guard and return their original receipt.

History cursors and database revisions

GET /v1/worklogs?task_id=... uses that task's history-order counter. Renames, archive/restore, worklog inserts/deletions, and end-only edits leave it unchanged because existing rows do not move in the history order. Unfiltered GET /v1/worklogs uses the global worklog counter, which conservatively invalidates on every worklog write. Task metadata changes leave that counter unchanged.

On the first page, storage reads the relevant counter and rows in one SQLite transaction. If more rows exist, next_cursor contains only the last returned ID and counter. Continuations submit after_id and after_revision, with optional task_id as the collection filter. In one read transaction, storage checks the revision, resolves the anchor start by ID, verifies collection membership, and reads rows after the stored start and ID. An outdated revision or missing, deleted, or out-of-scope anchor returns HTTP 409 with worklog_history_changed, requiring a fresh first page. Corrected starts determine chronology even when UUID creation order differs; equal starts across different tasks retain the ID tie-break.

SQLite triggers update these counters inside the worklog write transaction, including writes from other local processes. For example, a cursor ending at 10:00 would miss an unseen 09:00 worklog corrected to 11:00. Incrementing the task counter rejects that stale continuation instead of silently skipping the moved entry.

Why the guards coexist

Pagination counters do not cover stale task metadata writes. Conversely, using the server token for remote pagination would reject cursors after unrelated commands, such as renaming another task. It could work for server-mediated requests, and its new epoch would safely invalidate cursors after a restart. In-memory storage itself is not the correctness blocker.

Local clients have no server token. The TUI, CLI, and native macOS app can open the same local SQLite database concurrently, even if each presents one view. Database counters give all clients the same transactional pagination checks. The current split keeps task-history invalidation narrow while retaining the server's broader write and read-consistency guard.

Positive-duration migration and protocol upgrade

Schema migration 7 deletes completed worklogs with zero duration; they cover no time. It refuses databases containing negative durations and rolls back without changing any history. Negative durations indicate invalid stored data and require explicit database repair or a valid backup. Back up the database before upgrading. Protocol 4 removes timestamp and task fields from cursors. Upgrade the server and every client together and regenerate saved history and preview tokens. Incompatible pairs fail the health check. See ADR 0024.

Protocol 5 upgrade

Protocol 5 adds expected_name to task rename and archive requests. Upgrade the server and every client together; incompatible pairs fail the health check. No database migration is needed, and saved history and preview tokens stay valid. See ADR 0027.
