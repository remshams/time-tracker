Reading the diagrams

Read downward to follow time. Solid blue arrows are requests or calls. Dashed green arrows are responses. Gray boxes describe local work or scheduling. HTTP responses arrive only after a client request. The server has no WebSocket, event stream or subscription endpoint.

The TUI and CLI call RemoteApplication directly. Swift calls TrackerWorker, then the Rust C ABI bridge and its remote backend. The Swift/Rust boundary exchanges bridge JSON. The HTTP boundary uses the separate DTOs from tracker-protocol. In local mode, each client calls Rust and SQLite without these HTTP requests.

A snapshot contains all task records, each task's latest work start, the active worklog and a revision. It does not contain completed worklog history or report totals. Search, sorting and destination filtering use cached tasks. Elapsed time advances locally between reads.

Connect and load the first snapshot

Shared remote startup. No write runs during this exchange.

100%

  • Once a remote instance has completed its first refresh, later refreshes call only GET /v1/snapshot. A new instance checks health again.
  • A connected CLI task-list or tracking-status command reads this cache without another HTTP request.

02 / 08

Refreshes while a client is open

Each client schedules reads. The server does not initiate an update.

100%
  • The TUI runs one application request or background refresh at a time. Slow requests and queued work can delay polling. It continues polling while the terminal lacks focus.
  • The Swift worker implements ReportClient, so normal refreshes request daily reports. A snapshot-only injected client follows the fallback path. See the Swift investigation.
  • Swift pauses polls during sleep and busy work. Becoming visible, waking, manual refresh and local day rollover can request a read. The CLI has no background poll.

03 / 08

Start, switch or stop tracking

Example starts a new worklog. Task creation and task changes use the same guard and response pattern.

100%
  • Start while idle sends expected_active: null. Switching sends the previous active worklog ID. Selecting an already active task can return tracking_already_active.
  • Stop sends task_id: null, worklog_id: null and the expected active worklog ID. Idle requests can return tracking_already_idle.
  • The client supplies the event timestamp. Advancing a timer display sends no write. Swift may issue preflight snapshot reads and a later report read around this shared wire exchange.

04 / 08

Read history and report totals

History uses separate page reads. A report carries totals and a full snapshot.

100%
  • These are independent feature reads, shown consecutively for comparison. A client does not always issue all of them.
  • Task history updates cached tracking and relevant latest-work timestamps, but retains the previous full-snapshot write revision. Its response does not include the full task catalog. Global history and reports replace the full snapshot and revision.
  • The integer cursor revision tracks history consistency. It differs from the string server revision used by writes. A changed history can produce HTTP 409 with worklog_history_changed; restart pagination.
  • TUI live reports enqueue reads at most once per wall-clock second while the range contains now, plus calendar rollover and user refreshes. Historical ranges wait for user refresh. After an unavailable error, remote report reads have a 5-second cooldown.

05 / 08

Correct, move or delete a worklog

Expected worklog values protect the edit in addition to the global revision.

100%
  • PATCH and DELETE are alternatives. Deletion requires a completed worklog, so expected_end must be a timestamp.
  • Correction sends original and replacement start/end plus occurred_at. Move sends original task/start/end and destination task ID. Both allow null end times for active worklogs.
  • Swift correction and move preflight with snapshot and, when needed, bounded history reads. The bridge also refreshes just before the mutation. A preflight cannot prevent a later race; the server guard still decides whether the write is safe.
  • Successful mutation snapshots contain no completed history. Clients refresh affected history separately when needed.

06 / 08

A second client makes the write stale

A stale command is rejected and state is refreshed. The client does not automatically replay it.

100%
  • All new guarded writes share one server revision, so a write to an unrelated task can make a command stale. Matching idempotency-cache entries are checked before the revision.
  • An HTTP error triggers a Rust snapshot refresh for application operations. A transport outage does not trigger that same automatic refresh. Swift can add its own reconciliation read. Refresh itself reports errors directly.
  • Active-state mismatches return conflict. Worklog and history conflicts have more specific codes. A server restart creates a new revision epoch and an empty idempotency cache.
  • The labels epoch:7 and epoch:8 abbreviate the actual revision format <server-start UUID>:<sequence>. If error recovery also fails, the caller receives that recovery failure with the original error.

07 / 08

The server commits, but the response is lost

Transport retries a write once with identical bytes. The server can recognize a completed request.

100%
  • The transport uses at most two attempts for writes on send or body-read failures. GET and HEAD use one attempt. It does not retry an HTTP error response, invalid JSON or an oversized response.
  • The timeout is 5 seconds per attempt, with a 2-second connect timeout. There is no retry backoff. A client can wait for nearly two request timeouts on a write.
  • The server keeps the latest 1,024 successful request IDs in memory. Reusing an ID with a different route or payload returns HTTP 409. Restart or eviction removes this protection, so it is not a durable exactly-once guarantee.
  • After an uncertain create, RemoteApplication retains the task ID. A later same-name retry refreshes state first. It accepts an existing matching ID, or sends the same creation intent with a fresh revision and request ID.

08 / 08

Preview and confirm bulk archive

The confirmation uses the preview revision, even if background polling has fetched a newer snapshot.

100%
  • Preview sends at most five sample names and a count, rather than all candidate task IDs.
  • A changed revision rejects confirmation, even if the current client cache has already moved forward. Refresh and obtain a new preview.
  • The server validates the 15-minute timestamp tolerance during both preview and confirmation. A delayed confirmation can also fail with HTTP 400.

HTTP JSON DTO definitions · Server routes, guards and idempotency cache · RemoteApplication requests, cache and error recovery

A task has id, name, archived, created_at and updated_at. A task item wraps it as {task, latest_work_start}. A worklog has id, task_id, start and nullable end. Active worklogs have end: null. IDs and request IDs are UUID strings. Timestamps use RFC 3339; the remote adapter canonicalizes write times to microseconds. Durations use integer microseconds.

The server limits request bodies to 16 KiB; the remote transport limits responses to 16 MiB. Writes set Content-Type: application/json. The transport accepts root HTTP or HTTPS endpoints, disables redirects and configured proxies. The supplied server binds a loopback or assigned Tailscale address and validates Host. It serves plain HTTP; network protection comes from the deployment. There is no bearer-token field in this protocol.
