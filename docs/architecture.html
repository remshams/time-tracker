System overview

Runtime arrows mean “calls or accesses”. Each client selects one backend.

100%
  • The TUI, CLI and macOS app share the default local tt.db. tt-cli can also select another database with --db. The server uses tt-server.db by default.
  • Remote mode always uses the configured server. It keeps confirmed resource caches for display and does not fall back to a local database.
  • tt serve starts the HTTP server. New local and server databases start empty; existing tasks and worklogs remain stored.
  • Axum is the Rust HTTP framework. Its router maps methods and paths to async handlers, like an Express router. Bulk archive adds GET /v1/tasks/inactive-preview and POST /v1/tasks/archive-inactive.

Rust application, domain and storage

Solid arrows show use, ownership or calls. Dashed arrows show implementation of a contract.

100%
  • The application crate owns both client-facing use-case contracts and repository contracts. Type parameter R supplies the storage implementation.
  • Task queries use the cached catalog. Initialization and recovery read tasks and tracking in one transaction. Reports and history adopt only their scoped transaction values; clients select display refreshes explicitly.
  • Search ranking and calendar boundaries now live in the application crate. WorklogTimes validates corrections without a fabricated task ID. ApplicationFailure preserves the primary category, origin and failed recovery.
  • Bulk archive uses the preview timestamp, rechecks candidate IDs inside one transaction and rejects intervening work or changed metadata. SQLite also enforces timer and interval invariants.

TUI event loop and presentation

The event loop owns input, screen state, request polling and rendering.

100%
  • HTTP futures are polled alongside terminal input. Only one backend request runs at a time; AppState queues effects and applies their completion closures.
  • TrackingSession uses a monotonic elapsed clock. The redraw tick updates the visible timer without an HTTP request on every tick.
  • Task-list modes now own bulk-archive preview and confirmation. Generation guards reject stale dialog completions. Search and report calendar policy come from tracker-application.
  • Screens own their keymaps, actions and views. Shared components draw the header, dialogs and status line. TerminalGuard restores the terminal during normal exit and failures.
  • Remote refresh reads tasks and tracking independently and adopts a coherent revision pair. Queued writes retain reviewed task names, active worklog IDs and click times.

Automation CLI and command execution

tt-cli is a third client. It does not run the interactive terminal event loop.

100%
  • Clap parses the command and options. The CLI captures an operation time and validates user input before opening a database or making a server connection.
  • The backend selects a local application or the remote adapter. Command modules expose tasks, tracking, worklogs and reports using the same Rust rules as the other clients.
  • Bulk archive and worklog mutation tokens are bound to the selected backend. Local archive tokens retain the original preview time; remote tokens also retain server revision and expiry.
  • Successful output uses an ok/data JSON envelope. Failure output uses ok/error and maps semantic category, origin and recovery status to stable exit codes.
  • Remote open checks health only. Task commands explicitly read tasks, tracking status reads tracking, and reports resolve task names independently from task totals.

Swift application structure

The portable session depends on protocols. The native app supplies the implementations.

100%
  • TrackerClient is a separate Foundation-only Swift package. It contains models, dependency protocols, session coordination and feature state, without a dependency on Rust or macOS UI frameworks.
  • TrackerStore creates the worker, session, feature adapters and lifecycle observer. The window and AppKit status item share that session.
  • TimeTrackerApp now runs NSApplication directly. TrackerApplicationDelegate owns multiple native window controllers and installs the app menus. SwiftUI renders hosted panes inside those windows.
  • The serial worker queue owns every Rust handle operation, JSON decode and release. The Rust bridge has a persistent Tokio runtime for remote requests.
  • Xcode runs build-rust.sh and links the Rust static library through TimeTracker-Bridging-Header.h and TrackerBridge.h.

Swift to Rust bridge · exact call path

The baseline start-tracking diagram is retained from a0295f8. The updated table below lists Swift C calls at 52c3dd0 on 7 October 2026.

100%
  • TrackerStore injects one TrackerWorker into TrackerSession through TrackerClient and ReportClient. The portable session has no dependency on C declarations or Rust types.
  • RustBridge is a private Swift class inside TrackerWorker.swift. Bridge is a different type, a Rust struct whose application field holds the Backend enum.
  • Swift calls C functions synchronously on the worker queue. The caller awaits a continuation, so the main actor can keep handling UI events. The Tokio runtime's block_on waits on that same worker queue.
  • Inputs use withCString and remain valid for the C call. Rust parses task and worklog IDs, UTC timestamps and TaskName values before running a use case.
  • The start command compares the expected active ID in Backend::set_active_task_if_active, then delegates to set_active_task. It does not call a TrackerApplication method named set_active_task_if_active.
  • Rust allocates the handle with Box::into_raw and releases it in tt_bridge_close using Box::from_raw. Returned JSON and opening errors use CString::into_raw; Swift releases them with tt_bridge_string_free.
  • RustBridge.decode uses BridgeEnvelope<Value> to return a Swift model or throw BridgeFailure. TrackerSession rejects obsolete responses, composes selected observations and publishes feature changes through TrackerStore and its adapters. Command results carry no task-list state.
  • Xcode imports TrackerBridge.h through TimeTracker-Bridging-Header.h. build-rust.sh compiles libtracker_swift_bridge.a and Xcode links it into TimeTracker. HTTP communication begins inside Rust only when server mode is selected.

AppKit window ownership and native layout

AppKit owns windows, split items and toolbars. SwiftUI renders the hosted pane content.

100%
  • TrackerApplicationDelegate creates a shared TrackerStore and retains each TrackerWindowController. Closing the last window leaves the app and status item running.

Swift presentation updates

Arrows show change notifications and selective publication to UI observers.

100%
  • TrackerPresentationObserver compares the new presentation with its previous values. It invokes callbacks only for the parts that changed.
  • Timer ticks update the timer adapter and matching daily totals. An unchanged poll does not publish new task-list or history content.
  • The menu observer freezes its content while AppKit tracks an open menu. Menu clicks still ask the session to validate and perform the live action.
  • Healthy synchronization uses a report with totals and an authoritative snapshot. Swift polls every 5 seconds while visible, every 60 seconds while hidden, with failure backoff. Local display ticks run each second while visible and tracking; day rollover has its own timer.

A Swift tracking request through the remote backend

Time flows downward. Solid arrows are requests; dashed arrows are returned results. Diagram 07 and its table name the bridge methods.

100%
  • The client captures the action time before queuing the operation. The expected active worklog prevents a delayed command from switching or stopping a replacement timer.
  • The server uses WriteGuard.expected_revision and request_id. A successful response carries the mutation result and an authoritative snapshot with a new revision.
  • For local mode, the C bridge calls TrackerApplication<SqliteRepository> directly. The HTTP client and server columns disappear; the Swift queue and publication path stay the same.
  • The bridge JSON envelope and HTTP DTOs are separate formats. Swift decodes bridge models; the Rust remote adapter converts tracker-protocol DTOs into application and domain values.

Remote resources and cache ownership

Protocol 3 retains /v1 and requires a coordinated server and client update.

100%
  • Health checks do not load task or tracking resources. Reports and history do not carry a task catalog or global tracking attachment.
  • Task and tracking composition retries once on revision mismatch. Timer-only reads select tracking without loading the catalog; report-only reads return ID-based totals without task labels. A failed pair keeps the last coherent client state. Reports remain valid independently; running-total projection waits for matching report and tracking revisions and uses the echoed cutoff.
  • Each task, tracking, report and history observation retains its own revision and loaded state. Callers select TaskList, DailyTotals or TaskListWithTotals; matching observations publish together after at most two attempts. A failed refresh retains confirmed resources. A receipt never replaces newer caches. Recovery explicitly reads affected resources. The TUI and bridge enable coherent task command views, including creation preflight and recovery. Tracking preflight keeps its observations separate from the confirmed UI pair; a rejected command preserves that pair. A first tracking command initializes a coherent pair before checking reviewed intent. CLI commands retain narrow resource reads. Creation keeps its original task ID when a confirmed write has failed recovery. Rename and archive drafts retain reviewed names; tracking clicks retain the expected worklog ID and click time.
  • Preview responses return every candidate ID, time, period and revision. Clients resolve complete labels at that revision before confirmation.
